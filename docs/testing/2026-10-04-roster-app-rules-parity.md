# 名冊 App／Rules 邊界比對

日期：2026-10-04。追蹤：ROSTER-A2.1／PR #8；協作來源：PR #21 的 `990c2da`。

## 版本與證據界線

已讀取 `990c2da` 的命令實作；它與 PR #8 的 `firebase/roster.rules` 沒有差異。Claude 已補上「當天入班不能同日離班／轉點」檢查與明確錯誤碼，不重複修正。後續修改 `roster_commands.dart`、`roster_command_failure.dart` 或原命令測試前，須先合併或 cherry-pick `990c2da`；改為「取消入班」要先由使用者確認，並一併設計 Rules。

本輪逐一靜態比對命令與 Rules，並以本機記憶體 Store 執行四組診斷，確認 App planner 會接受下列輸入。診斷使用 PR #8 的 `a23343f`；四組情境均未觸及 `990c2da` 新增的同日保護，因此結果同樣適用該修正版本。**未重跑 Rules Emulator，也未操作正式資料；以下 Rules 拒絕結論來自明確條件比對，不冒充端到端驗證。** 本輪只交付檢查結果，未變更這三個協作檔案或 Rules。

## 找到的落差（尚未修復）

### P2：已預排離班，再於離班前轉點

- 前置：學生在 A，期間 `2020-01-01 → 2026-10-15`，沒有更晚的期間。今天為 10/4，指定 10/10 轉到 B。
- App `_membership` 接受，關閉 A 於 10/10，但建立 B 的結束日固定為 `9999-12-31`。
- Rules `transferPeriod` 要求原期間結束日等於新期間結束日；`2026-10-15 != 9999-12-31`，因此交易會遭拒。對應命令約 728–747 行、Rules 233–238 行。
- 修正前要明確決定：轉點是否保留原定離班日。不要藉放寬 Rules 隱式取消既有離班安排。

### P2：連續預排兩次跨據點轉班

- 前置：今天 10/4，學生目前 A；已排 10/10 到 B，再排 10/20 到 C。管理者有 A、B、C 權限。
- App 接受第二次轉點，當前投影仍是 A，但操作收據只列改動的 `[C, B]`。
- `students` 更新要求 `fresh(op, request.resource.data.locationId)`，亦即當前 A 必須在收據據點內；A 缺席導致拒絕。對應命令約 715–723、750–818 行、Rules 30–33、363–364 行。
- 同類風險：預排 A→B 後，對未來 B 的期間再排離班。應讓收據包含 Rules 所需的當前授權據點，並明確驗證該據點權限。

### P2：一般老師將已停課的課次改回有上課

- App `_session` 只在新狀態為 `cancelled` 時要求管理者；一般老師提交 `cancelled → held` 可通過 planner。
- `DailyRosterCubit.setSession` 也只檢查新的 cancelled 狀態；尚未完整操作畫面確認所有入口是否可達。
- Rules 201 行要求「原本 cancelled 的課次只能由管理者修改」。需要補上舊狀態檢查與明確訊息；不能因 Rules 拒絕就說老師所有權限都失效。

### P3：以開放期間的結束日作為入班日

- `_enroll` 接受 `startDate=9999-12-31`，寫出的 start/end 相同；重新入班也有相同邊界風險。
- Rules 388 行要求 start < end。應在命令層拒絕這個 sentinel 日期。
- 這是命令層缺口，**未證明目前日期選擇器能輸入此值**；優先度低於前三項。

## 逐項核對摘要

| 操作 | 已核對的主要條件 | 本輪結果 |
| --- | --- | --- |
| saveRecord／saveRecords | 非未來日期、據點、有效就讀區間、停課、欄位值、整批收據 | 正常資料路徑未發現新的日期落差；裝置日期與伺服器日期跨午夜仍需實測 |
| setSession | 日期、停課原因、角色、舊狀態、revision | 找到一般老師恢復停課的漏檢；held 狀態的 reason 亦未像 Rules 一律檢查型別及 400 字上限，未證明 UI 可輸入非法值 |
| enrollStudent | 管理者、據點、profile、單一期間、摘要／錢包／索引 | 找到 sentinel 造成零長度期間；一般未來入班沒有被 Rules 全面禁止 |
| updateProfile | 當日有效據點、可改欄位、型別、同步姓名摘要 | 正常資料路徑未發現新增落差；舊資料格式不合法另需資料盤點 |
| changeEnrollment：轉點 | 同日起訖、最後期間、來源／目標據點、收據 | 同日問題由 `990c2da` 處理；另找到有限結束日與連續未來轉點問題 |
| changeEnrollment：封存／重新入班 | 是否有有效期間、不得穿過後续期間、非零長度 | 同日封存已修；未來投影收據與 sentinel 邊界仍需處理 |
| correctEnrollment | 日期有序、相鄰期間不重疊、全部歷史據點授權、原因 | 正常替換路徑未發現新增落差；不包含新增「取消入班」行為 |
| redeemRibbon | 當日有效據點、正整數額度、餘額、錢包／事件 | 正常資料路徑未發現新增落差；已離班學生沿用最近據點的既有語意保留 |
| recoverOperation／原 ID 重試 | 原 uid、hash、據點、既有收據 | 未發現新增落差；不存在收據不當成一定未寫入 |

## 下一輪驗證方式

將上述具體輸入加入 Dart planner → 真實 Rules Emulator 的交易重播；不能只測記憶體 Store。需要同時驗證成功案例與明確拒絕案例，特別是當天、未來、原定離班日、A→B→C、受限據點與台灣午夜邊界。先納入 `990c2da`，再修命令前置檢查；任何業務語意變更另行確認。
