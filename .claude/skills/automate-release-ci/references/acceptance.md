# 驗收與證據

每項需求分别標記：未實作、已配置、模擬測試通過、真實雲端實跑通過、目的平台 API 確認、通知已送出、收件方確認。不是每項都需要所有等級；但各等級不能互相冒充。每筆證據帶時間、環境、commit、release／job ID、結果與連結，不含秘密或業務資料。

## 先寫驗收矩陣，再實作對應路徑

| 情境 | 隔離測試應證明 | 真實環境驗收／邊界 |
| --- | --- | --- |
| 正常發布 | 精確關聯 release，查驗就緒才產生成功通知 | 單一 trigger → 真實建置／簽章／部署 → 真實事件 → 查驗 → 通知；保存各環節證據 |
| 品質閘門失敗 | 後續上傳／部署不會執行 | 授權的測試 branch/job 主動失敗，確認停止和失敗通知；不破壞正式分支 |
| 壞簽章／竄改 | 拒絕事件，不能啟動發布或讀敏感紀錄 | 對測試接收端發送非法簽章，核對拒絕狀態與無副作用 |
| 重複／亂序／錯版本 | 不覆寫較新的結果、不誤發成功、不永久漏信 | 測試 release 重送事件或使用官方 redelivery；不得對真實未就緒 release 偽造成功 |
| 接收後中斷／佇列失敗 | ACK 前持久化、重試能修復半完成狀態 | 隔離服務注入一次 enqueue／啟動失敗，恢復後證明工作繼續 |
| 平台回報 failed | 與授權錯誤、CI 失敗分開分類 | 用安全的測試來源或服務商 sandbox 走完整失敗通知；模擬 API 不算真實平台失敗 |
| 長時間 pending／無 webhook | 有截止時間，結果 unknown，資源停止消耗 | 專用測試 release／可縮短的測試 deadline 驗证排程與實際寄信；不假裝已驗正式等待時長 |
| 401／403 | 停止盲目重試，結果為授權不可用 | 使用專用無效測試憑證，不撤銷正式 key；確認獨立告警真的可送達 |
| 429／5xx／網路中斷 | 有限退避、不誤報 ready | 測試 adapter／proxy 注入，標記模擬範圍與恢復結果 |
| job 取消／逾時／runner 不可用 | lease 可回收、鎖可解除，不無限排隊 | 專用測試 job 取消一次，核對 watchdog、通知及下一次可啟動 |
| 通知失敗 | 結果與送信狀態分開，重試可送達 | 專用測試 recipient／transport 故障後恢復；確認不依賴失效的主要 token |
| 並行／重跑 | 配號與鎖範圍正確，同 release 不重複上傳 | 授權測試 lane 並行；外部寫入 outcome 不明先查詢，不直接再上傳 |
| 完整自動簽章 | 正確區分 auth key、簽章私鑰與 profile | 若屬需求，乾淨 runner 真實取得／建立資產並產生合格輸出；固定資產成功不能替代此驗收 |

## 安全地做端到端失敗測試

使用獨立測試 release ID、非正式接收環境及合成 metadata，通知主旨標記「流程測試／未發布新版」。收件管道與對象沿用使用者授權；未授權寄信就先完成可審閱內容，再取得所需授權。無需為單元測試連接正式帳號。

測試 adapter、假的 API、假時鐘可以驗證真實 CLI 的分支與 artifact，但無法證明 Apple／公司平台真的傳遞事件、scheduler 真的執行，或 Email 抵達。不可直接向正式 `/finish` 寫 ready 來充當端到端成功，也不可把人工啟動 verifier 說成 webhook 自動触發。

如果環境不允許某種故障注入，記錄原因、替代測試及未驗項目，讓使用者知道覆蓋缺口；不要把清單全打勾。使用者若接受有限範圍，依該範圍交付，不藉此擴張其他需求。

## 最後交付

交付可重複執行的單一入口、已提交的 pipeline／腳本、外部設定位置與權限、版本與來源對應、最新驗收證據、失敗恢復與日常維護方式。遵守目標 repository 的 commit／PR 授權；不要求每家公司採相同 branch/tag 命名。

明確回答：日常發布是否已無人工步驟？簽章建立／更新是否已自動？成功信是否實際收到？失敗與逾時是否真正寄信驗收？尚有哪些帳號條款、權限或續期需要管理者？

報告主體保持簡短，完整矩陣存放 repository。只確認 publisher 成功時說「寄信工作完成」；有供應商送達紀錄或收件方確認後，才說「送達／已收到」。部署 CLI 尾端清理警告与部署本身分别核對，不因單一 exit code 就重複外部操作。
