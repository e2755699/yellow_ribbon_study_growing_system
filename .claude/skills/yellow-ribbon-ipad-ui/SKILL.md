# 黃絲帶 iPad 介面開發

將 Apple 的互動與版面原則落實到本專案的正式 Flutter 元件。目標是讓使用者知道「可以按什麼、它影響哪裡、下一步是什麼」，並讓相關頁面的配色、位置與間距一致。

## 先定位要改的畫面

1. 讀 repository 根目錄的 `AGENTS.md`、`CLAUDE.md`、`docs/design-system.md`；路徑均以實際 checkout 為準，不依賴某台電腦的絕對路徑。
2. 根據使用者指示、截圖與目前可執行版本，定位元件及呼叫它的頁面。區分入口按鈕、外層排版、開啟後的內容；只修被指出的問題。例如「隱私權按鈕和位置」不代表重排政策內文。
3. 用簡短說明指出修改對象、問題及預期效果。能從現有資訊確定就開始；只有辨識不到畫面或有實質歧義時才問一個精準問題。使用者正在提供標註截圖時，先接收證據，不搶先重設計其他部分。
4. 比較同一主題下鄰近的正式畫面，確認其主次操作與對齊基準。不要拿另一套主題或孤立的 Widgetbook 展示當作唯一參考。

## 設計依據

- **視覺樣式以 `docs/design-guideline.md` 為準**（頁首／資訊列／卡片版型、主題 token 用色、元件選用、禁止事項）。先讀 [視覺樣式速查](references/visual-style.md)，新畫面依該文件的檢查清單交付。
- 修改視覺或互動前，讀 [Apple iPad 設計依據](references/apple-ipad-guidance.md) 的相關段落。引用數字時分清 Apple 建議、本專案約定與目前程式現況。
- 決定尺寸、顏色、元件或驗證方法時，讀 [專案實作與驗收](references/project-implementation.md)。檔內數值是 token 種子值，執行時仍讀使用者選擇的主題。
- HIG 會更新；需要新版系統功能或原生元件行為時，重新查看對應官方來源。不要把 visionOS、macOS 的專屬規範套到 iPad，也不要把 HIG 當作 App Store 審核通過保證。

## 做出可實作的版面決定

在任務紀錄或進度說明留下精簡的設計決定，足夠讓人核對即可：

| 決定 | 必須說清楚的內容 |
| --- | --- |
| 操作層級 | 哪個是主操作、哪個是次操作／輔助入口；不能每個按鈕都同樣搶眼。 |
| 放置位置 | 影響單張卡片的動作靠近卡片；全頁工具放共同工具區。說明與既有基準線及 SafeArea 的關係。 |
| 尺寸與間距 | 分別列視覺大小、實際點擊範圍、內距、外距與所用 token。留白不能只靠放大按鈕。 |
| 窄版與放大文字 | 空間不足時換行、重排或收納哪些次要操作；主要操作仍能找到與觸及。 |
| 主題與狀態 | 哪些語意色／字級、pressed／focus／disabled 狀態，以及主題從哪個 scope 傳入。 |

這是實作依據，不是每次都要使用者批准的表單。沿用已給的授權；不額外創造固定審批關卡。

## 接到既有系統

- 遵循 `theme definition → SystemTheme → production components → pages`。外層 `SystemThemeScope` 管理選擇／訂閱，展示元件只讀 `SystemTheme.of(context)`，接收資料與 callback。
- 使用現有 `SystemPage`、`SystemSectionCard` 和共同表面樣式；不新增頁面專用色票、ThemeExtension 或展示專用仿製元件。
- 修入口時同時檢查 host 的排列與主題傳遞。只給小按鈕包另一個 scope，可能讓它與旁邊主按鈕來自不同主題。先查資料流再修正，不為單一問題擅自遷移整個 App。
- 依可用空間調整版面，避免絕對座標與螢幕縮放把觸控範圍縮小。保留登入、返回、儲存、權限與附件行為；視覺變更不順便改資料／政策內容。
- 更新受影響的正式元件、`docs/design-system-components.json`、Widgetbook cases；展示同一個 production class。目錄由 build_runner 產生。主題目錄維持動態，不列死允許的主題 ID。
- 本 skill 管介面判斷與驗證；若任務另已啟用專案功能開發流程，將設計與驗收結果寫進該流程既有 working doc，不另建重複流程。
